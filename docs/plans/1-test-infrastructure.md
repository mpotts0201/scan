## 1. Goal

Stand up the headless test toolchain so every later issue can ship with tests,
and stop there. After this PR, `npx jest` runs green on a jest-expo preset that
matches Expo SDK 54; `@testing-library/react-native` (RNTL) can render a React
Native component tree in Node with no simulator; `better-sqlite3` is present as
a devDependency and demonstrably loadable from a test, which is what makes the
already-recorded dual-SQLite-driver decision viable in issue #2; and the
currently commented-out Tests step in `.github/workflows/ci.yml` is live and
green. Two placeholder tests exist — one pure-Node unit test, one component
test — and they are chosen to *prove the toolchain*, not to test app behavior,
because there is no app behavior yet. No app feature code, no coverage
thresholds, no E2E.

Assumptions I am planning against (correct me if any is wrong):

- Node 20 locally (verified: `v20.20.2`) and Node 20 in CI (verified in
  `ci.yml`). This constrains `better-sqlite3` — see §4.
- `src/` does not exist yet; this PR creates it, containing only tests.
- `tsconfig.json` has no `include`/`exclude` of its own, so `tsc --noEmit`
  typechecks every `.ts`/`.tsx` in the repo, including test files. Test files
  therefore need ambient Jest types to pass `npm run typecheck`.
- The gate (`typecheck`, `npx jest`, `export:check`) must stay green; nothing
  here may perturb `export:check`, which is why no runtime dependency changes.

### 3.1 No `babel.config.js` is needed (verified)

`jest-expo`'s preset calls `resolveBabelConfig(process.cwd())`; when the
project has no `.babelrc` / `.babelrc.js` / `babel.config.js`, it falls back to
`require.resolve('expo/internal/babel-preset')`. That path resolves in this
repo today (`/workspace/node_modules/expo/internal/babel-preset.js`). TS/TSX
transform therefore works out of the box. Adding a `babel.config.js` would
*change* behavior (it disables the fallback and hands config resolution back to
Babel) for zero gain.

### 3.2 No Jest setup file is needed (verified against SDK 54 / RNTL 13)

- The `jest-expo` preset already appends its own `setupFiles` entry
  (`jest-expo/src/preset/setup.js`), which installs the Expo/RN native-module
  mocks — including `expo-status-bar`, `expo-camera`, `expo-sqlite`.
- RNTL has shipped its matchers built in since v12.4; `@testing-library/jest-native`
  is deprecated and **must not** be installed.
- RNTL auto-registers its matchers and auto-cleans up after each test when a
  global `afterEach` exists, which it does under Jest.

So `setupFilesAfterEach`/`setupFiles` stay empty in our config. If a future
issue needs global test setup (e.g. a fake timer policy), that issue adds the
file — this one does not pre-build the hook.

### 3.3 Where the "trivial component" comes from — decision

**Decision: a fixture component defined inside `render-smoke.test.tsx`.** Not
`App.tsx`.

Rationale, concretely: `App.tsx` is scaffold text that issue #3+ will delete or
rewrite. If the toolchain smoke test asserts on App's rendered content, then
the first UI issue makes the *infrastructure* test fail, and whoever is on that
issue has to decide whether they broke Jest or just changed a string — exactly
the false signal a smoke test exists to avoid. A self-contained fixture pins
the test to the thing it is actually testing (RNTL + the preset can render RN
primitives headlessly) and has no coupling to app code. Secondary benefit: it
does not depend on the preset mocking `expo-status-bar`, so a failure points at
RNTL rather than at Expo's mock table.

The fixture is 4–5 lines of TSX inside the test file, uses only `View` and
`Text` from `react-native`, and exposes a `testID`. It is **not** exported and
**not** placed in `src/` as a production file.

## 4. Public interface

For this issue "public interface" means: the exact files, the exact config, and
the exact dependency set. This is the contract.

### 4.1 `jest.config.js` (exact intended contents)

```js
// Jest config for Expo SDK 54. Kept deliberately minimal:
// - `jest-expo` supplies transform, transformIgnorePatterns, the RN test
//   environment, and the Expo/RN native-module mocks.
// - No setup file: RNTL >= 12.4 registers its matchers and auto-cleanup itself.
/** @type {import('jest').Config} */
module.exports = {
  preset: 'jest-expo',
  testPathIgnorePatterns: ['/node_modules/', '/dist/', '/.expo/'],
};
```

Notes for the implementer:

- **`.js`, not `.ts`.** `expo/tsconfig.base` already lists
  `"${configDir}/jest.config.js"` in its `exclude`, so a `.js` config is
  invisible to `tsc --noEmit` with zero tsconfig edits. A `jest.config.ts`
  would be typechecked and would drag `@types/jest`'s `Config` resolution into
  the app typecheck for no benefit. **Do not modify `tsconfig.json` in this PR.**
- **Do not re-declare `transformIgnorePatterns`.** The Expo docs snippet shows
  one, but `jest-expo@54`'s preset already sets a broader, correct value.
  Copying the doc snippet would *narrow* it and is a known cause of
  "Unexpected token 'export'" from `node_modules`.
- `testPathIgnorePatterns` covers `dist/` (left behind by
  `npm run export:check`) and `.expo/`, both gitignored but present in a
  developer's working tree. Without this, a local `export:check` run can put
  files in Jest's discovery path. It is two extra entries, not a policy.
- **Do not** set `roots`. It narrows the haste map as well as test discovery
  and can perturb RN module resolution; `testPathIgnorePatterns` only affects
  test discovery, which is all we want.
- **Do not** use the multi-project `jest-expo/universal` preset or add
  `projects`. Single project is sufficient here. If issue #2 finds that the
  RN-flavored environment is hostile to `better-sqlite3`, the escape hatch is a
  second project on the `jest-expo/node` preset — but §4.4 exists precisely so
  we learn that *now*, in this PR, rather than in #2.

### 4.3 Install commands (exact, in this order)

```sh
# Expo-coupled: version comes from expo's bundledNativeModules pin (~54.0.18).
npx expo install jest-expo --dev

# Not Expo-coupled. Explicit versions on purpose — see the pin rationale below.
npm install --save-dev jest@~29.7.0 @types/jest@^29.5.14 \
  @testing-library/react-native@^13.3.3 react-test-renderer@19.1.0 \
  better-sqlite3@^12.11.1 @types/better-sqlite3@^9.6.0
```

Do **not** run `npx expo install` for the second group. `expo install` only
pins packages listed in `expo`'s `bundledNativeModules.json`; `jest` and RNTL
are not listed, so it would silently install *latest* — which is precisely the
failure mode the pins below prevent.

Why each version is pinned where it is (all verified against the registry
today, not recalled):

- **`jest-expo@~54.0.18`** — `expo@54.0.36`'s `bundledNativeModules.json` pins
  `"jest-expo": "~54.0.18"`. This is the SDK-54-correct major; anything else
  violates the SDK pin.
- **`jest@~29.7.0`, `@types/jest@^29.5.14` — not 30.** `jest-expo@54.0.18`'s
  own dependencies are `babel-jest@^29.2.1`, `jest-snapshot@^29.2.1`,
  `@jest/globals@^29.2.1`, `jest-environment-jsdom@^29.2.1`, and
  `react-native@0.81.5` itself depends on `babel-jest@^29.7.0` /
  `jest-environment-node@^29.7.0`. Jest 30 is currently latest, so an
  unpinned install gets you a v30 runner driving v29 internals: two copies of
  `expect`, and snapshot/transformer interface mismatches. Pin to 29.
- **`@testing-library/react-native@^13.3.3` — not 14.** RNTL 14 replaces
  `react-test-renderer` with a peer on the new `test-renderer@^1.0.0` package;
  RNTL 13's peer set (`react >= 18.2`, `react-native >= 0.71`,
  `react-test-renderer >= 18.2`) is exactly satisfied by what jest-expo 54
  already brings. 13 is the low-risk line for this stack.
- **`react-test-renderer@19.1.0` (exact).** `jest-expo@54.0.18` depends on it
  at exactly `19.1.0`, so hoisting would probably satisfy RNTL's peer — but
  RNTL declares it as a *direct* peer and relying on a transitive hoist means a
  jest-expo patch release can break our install. One explicit line removes the
  coupling. Pinned exact to match `react@19.1.0`.
- **`better-sqlite3@^12.11.1` — NOT `^13`.** `better-sqlite3@13.x` declares
  `engines: { node: ">=22" }`; this repo and CI are on Node 20. `12.11.1`
  declares `node: "20.x || 22.x || 23.x || 24.x || 25.x || 26.x"`. Installing
  latest here fails or warns on Node 20 in CI. If someone later moves CI to
  Node 22, v13 becomes available — that is a separate issue, and CI's Node
  version must **not** change in this PR.
- **`@types/better-sqlite3@^9.6.0`** — `better-sqlite3` ships no `.d.ts` of its
  own (verified: no types/typings field, no `.d.ts` in the tarball). Under
  `strict`, importing it from a `.ts` test without types fails
  `npm run typecheck` with TS7016.

### 4.4 `src/__tests__/sqlite-smoke.test.ts` — required behavior

The unit placeholder is deliberately not `expect(1 + 1).toBe(2)`. It must, in
one `describe`:

1. `import Database from 'better-sqlite3'` (default import; `esModuleInterop`
   is on in `expo/tsconfig.base`).
2. Open an in-memory database (`new Database(':memory:')`).
3. Create a table, insert a row, read it back, assert the round-tripped value.
4. Close the database in `afterAll`/`finally` so the suite exits cleanly.

This is what actually discharges the risk in this issue: it proves the native
Node addon loads *inside the jest-expo RN-flavored test environment* before
issue #2 depends on it. A trivial arithmetic assertion would prove nothing that
`npx jest` exiting 0 doesn't already prove.

Constraint restated for the auditor: `better-sqlite3` appears in
`devDependencies` and is imported **only** from files under `**/__tests__/**`.
It is a native Node addon, never bundled by Metro, never reachable from
`App.tsx`, and therefore does **not** violate the Expo Go / no-native-modules
constraint. `npm run export:check` must remain green, which is the mechanical
proof of that.

### 4.5 `src/__tests__/render-smoke.test.tsx` — required behavior

1. Define a fixture component inside the file — signature only:

   ```tsx
   function Hello(props: { name: string }): React.JSX.Element
   ```

   rendering `<View><Text testID="greeting">Hello, {name}</Text></View>` using
   only `react-native` imports.
2. `render(<Hello name="…" />)` from `@testing-library/react-native`.
3. Assert the text is found by role/testID/text via RNTL's queries, and use at
   least one **built-in RNTL matcher** (e.g. `toBeOnTheScreen`) so the test
   fails loudly if someone later adds the deprecated
   `@testing-library/jest-native`.
4. No snapshot assertions. Snapshots on a fixture are noise, and they would
   commit a `__snapshots__` directory this issue does not want to own.

Replace the trailing comment block:

```yaml
      # - name: Tests
      #   run: npx jest --ci
```

with:


CI note (not a change, just an expectation to set): `npm ci` will now build or
download a `better-sqlite3` binary. `prebuild-install || node-gyp rebuild`

otherwise compile from source with the toolchain already on the runner. Either
way it works; the `npm ci` step may get noticeably slower. If it turns out
*no* Node 20 prebuild is published for 12.11.1 and the compile is unacceptably
slow, report it rather than adding a caching step in this PR.

## 5. Data model

**No SQLite schema in this issue, and no migration.** The `:memory:` database
in `sqlite-smoke.test.ts` creates and drops a throwaway table inside the test;
it is not a schema, it must not be given a migration, and no other file may
import it.

The real schema and the driver interface it sits behind land in issue #2. Two
forward constraints this plan fixes now so #2 does not have to relitigate them:

- The driver interface will have two implementations (expo-sqlite in app,
  better-sqlite3 in tests), per the existing DECISIONS.md entry "Dual SQLite
  drivers". This PR makes the second one installable; it does **not** define
  the interface.
- Any future table representing allergen/label data must distinguish declared
  absent / declared present / no data. Out of scope here; recorded so #2's plan
  inherits it.

## 7. Test surface

This issue's deliverable *is* the test surface, so this section says what the
two placeholders must be worth — and, more importantly, what they must not
become.

| Module under test | Property that matters |
|---|---|
| The Jest/Babel/Expo toolchain itself | TS and TSX under `src/` transform and execute; the `jest-expo` preset resolves; the process exits cleanly. |
| `better-sqlite3` in the test environment | The native addon loads inside the jest-expo runner, and SQL executes and round-trips values. This is the load-bearing assertion for issue #2. |
| RNTL + react-test-renderer | An RN component tree renders headlessly; RNTL queries locate nodes; RNTL's built-in matchers are registered without a setup file. |

Properties deliberately **not** asserted, and why:

- Nothing about `App.tsx` (§3.3).
- No snapshots (churn with zero signal on a fixture).
- No coverage thresholds (out of scope per the issue; a threshold on a repo
  with no app code is meaningless and would have to be re-tuned every PR).
- No assertions on jest-expo's internals (preset contents, mock table). Those
  are Expo's to change; asserting them makes SDK patch bumps our problem.

Guidance for whoever writes issue #2's tests: these two files are *smoke*
tests. When real data-layer tests exist, `sqlite-smoke.test.ts` may be deleted
outright — its only job is to be the first thing that proves the pipeline, and
it stops earning its keep once a real driver test exercises the same path.
`render-smoke.test.tsx` should survive longer, because it stays independent of
app churn.

## 9. DECISIONS.md

The existing entry "Dual SQLite drivers: expo-sqlite in app, better-sqlite3 in
tests" already covers *why* `better-sqlite3` is here. **Do not duplicate it.**

There is one new tradeoff worth recording, because without it a future agent
will "helpfully" run `npm update` or `npx expo install jest --dev`, land Jest
30 / RNTL 14 / better-sqlite3 13, and break the suite in a way that looks like
a flake:

> **2026-09-02 — Test stack pinned to Jest 29 / RNTL 13 / better-sqlite3 12**
> Decision: `jest@~29.7.0`, `@testing-library/react-native@^13`,
> `better-sqlite3@^12`, `jest-expo@~54.0.18` — none installed at latest.
> Instead of: latest majors.
> Because: `jest-expo@54` and `react-native@0.81.5` depend on Jest 29
> internals; RNTL 14 swaps `react-test-renderer` for a new `test-renderer`
> peer; `better-sqlite3@13` requires Node >= 22 while CI runs Node 20.
> Revisit when: the SDK pin moves off 54, or CI moves to Node 22.

This entry has been appended to `DECISIONS.md` on this branch by the architect.
Everything else in this issue is mechanical setup, not a tradeoff — no other
entry is warranted.
