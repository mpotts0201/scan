# Plan — Issue #1: Test infrastructure (jest-expo + RNTL + Node SQLite)

Status: proposed (amended 2026-09-02, §11) · Author: architect · Branch: `feat/1-test-infrastructure`

## 1. Goal

Stand up the headless test toolchain so every later issue can ship with tests, and stop there. After
this PR: `npx jest` is green on a jest-expo preset matching Expo SDK 54; RNTL renders an RN tree in
Node with no simulator; `better-sqlite3` is a devDependency and demonstrably loadable from a test
(which is what makes the recorded dual-SQLite-driver decision viable in #2); and the commented-out
Tests step in `ci.yml` is live and green. Two placeholder tests prove *the toolchain*, not app
behavior — there is none yet. No feature code, no coverage thresholds, no E2E.

Assumptions (correct me if wrong): Node 20 locally (verified `v20.20.2`) and in CI, which constrains
`better-sqlite3` (§4.3); `src/` does not exist yet and this PR creates it containing only tests;
`tsconfig.json` has no `include`/`exclude`, so `tsc --noEmit` typechecks test files and they need
ambient Jest types; nothing here may perturb `export:check`, hence no runtime dependency changes.

Explicitly **not** created — do not add "just in case":

### 3.1 No `babel.config.js`

`jest-expo`'s preset falls back to `expo/internal/babel-preset` when no Babel config exists
(verified: that path resolves here), so TS/TSX transform works out of the box. Adding a config
*disables* that fallback for zero gain.

### 3.2 No Jest setup file, no `__mocks__`

The preset already appends `setupFiles` installing the Expo/RN mocks (`expo-status-bar`,
`expo-camera`, `expo-sqlite`), and RNTL has shipped matchers built in since v12.4, auto-registering
them plus cleanup under Jest — so `@testing-library/jest-native` is deprecated and **must not** be
installed. A future issue needing global setup adds the file then.

### 3.3 The trivial component is a fixture, not `App.tsx` — ruling

`App.tsx` is scaffold that issue #3+ will rewrite. If the smoke test asserted on App's content, the
first UI issue would break the *infrastructure* test and force whoever is on it to decide whether
Jest broke or a string changed — exactly the false signal a smoke test exists to avoid. The fixture
is 4–5 lines of TSX inside `render-smoke.test.tsx`, uses only `View`/`Text`, is not exported, and is
not a `src/` production file.

## 4. Public interface

Here that means the exact files, config, and dependency set. This is the contract.

### 4.1 `jest.config.js` (exact intended contents)

```js
// Jest config for Expo SDK 54. Kept deliberately minimal:
// - `jest-expo` supplies transform, transformIgnorePatterns, the RN test
//   environment, and the Expo/RN native-module mocks.
// - No setup file: RNTL >= 12.4 registers its matchers and auto-cleanup itself.
/** @type {import('jest').Config} */
module.exports = {
  preset: 'jest-expo',
  testPathIgnorePatterns: ['/node_modules/', '/dist/', '/.expo/'],
};
```

- **`.js`, not `.ts`** — `expo/tsconfig.base` already excludes `jest.config.js`, so it is invisible
  to `tsc --noEmit`. **Do not modify `tsconfig.json` in this PR.**
- **Do not re-declare `transformIgnorePatterns`** — the Expo docs snippet narrows `jest-expo@54`'s
  broader correct value, a known cause of "Unexpected token 'export'" from `node_modules`.
- `dist/` and `.expo/` are ignored because `export:check` leaves them inside Jest's discovery path.
- **Do not** set `roots` (narrows the haste map, perturbs RN resolution) or use the
  `jest-expo/universal` multi-project preset. If the RN-flavored environment proves hostile to
  `better-sqlite3`, the escape hatch is a second project on `jest-expo/node`; §4.4 exists to learn
  that now, not in #2.

### 4.2 `package.json` changes (exact)

Script: `"test": "jest"` (not `--watchAll`; every consumer is non-interactive).

```json
"devDependencies": {
  "@testing-library/react-native": "^13.3.3",
  "@types/better-sqlite3": "^9.6.0",

  "@types/react": "~19.1.0",
  "better-sqlite3": "~12.9.0",
  "jest": "~29.7.0",

  "react-test-renderer": "19.1.0",
  "typescript": "~5.9.2"
}
```

### 4.3 Install commands (exact, in this order)

```sh
# Expo-coupled: version comes from expo's bundledNativeModules pin (~54.0.18).
npx expo install jest-expo --dev

# Not Expo-coupled. Explicit versions on purpose — see the pin rationale below.
npm install --save-dev jest@~29.7.0 @types/jest@^29.5.14 \
  @testing-library/react-native@^13.3.3 react-test-renderer@19.1.0 \
  better-sqlite3@~12.9.0 @types/better-sqlite3@^9.6.0
```

Do **not** use `npx expo install` for the second group: it only pins packages in
`bundledNativeModules.json` and silently installs *latest* for the rest — the failure mode these
pins prevent. One bullet per pin, each verified against the registry/releases today:

- **`jest-expo@~54.0.18`** — the exact spec in `expo@54.0.36`'s `bundledNativeModules.json`;
  anything else violates the SDK pin.
- **`jest@~29.7.0` / `@types/jest@^29.5.14`, not 30** — `jest-expo@54.0.18` and `react-native@0.81.5`
  depend on `babel-jest` / `jest-snapshot` / `@jest/globals` / `jest-environment-*` at `^29`; a v30
  runner over v29 internals means two copies of `expect` and snapshot/transformer mismatches.
- **`@testing-library/react-native@^13.3.3`, not 14** — RNTL 14 swaps `react-test-renderer` for a
  new `test-renderer@^1` peer that jest-expo 54 does not provide.
- **`react-test-renderer@19.1.0` (exact)** — RNTL declares it a *direct* peer; relying on
  jest-expo's transitive hoist lets a jest-expo patch release break our install.
- **`better-sqlite3@~12.9.0`, not `^12` and not `^13`** — two Node 20 ceilings. 13.x declares
  `engines: node >= 22`. Within 12.x, v12.10.0's notes say it "remove[d] EOL builds (Node.js v20,
  v23)": its assets ship linux-x64 prebuilds for ABI 127/137/141/147 only, while 12.9.0 still ships
  ABI 115 (Node 20) with identical deps. Without a prebuild the install script's `prebuild-install
  || node-gyp rebuild` compiles from source (§11). `~12.9.0` is the widest range admitting only
  prebuild-bearing releases: 12.9.1 also ships ABI 115 but was **never published to npm**
  (`npm view better-sqlite3@12.9.1` 404s), so `~12.9.1` is unresolvable, and `^12` resolves to
  12.11.1 and reinstates the compile. Widening waits on Node 22 (§10 Q2); CI's Node version must
  **not** change in this PR.
- **`@types/better-sqlite3@^9.6.0`** — the package ships no `.d.ts` (verified), so a `.ts` import
  fails `typecheck` with TS7016 under `strict`.

### 4.4 `src/__tests__/sqlite-smoke.test.ts` — required behavior

Not `expect(1 + 1).toBe(2)`. In one `describe`: default-import `Database` from `better-sqlite3`
(`esModuleInterop` is on), open `new Database(':memory:')`, create a table, insert, read back and
assert the value, then close in `afterAll`/`finally` so the suite exits cleanly. This discharges the
issue's real risk — the native addon loading *inside the jest-expo RN-flavored environment* before
#2 depends on it. For the auditor: it is a devDependency imported only from `**/__tests__/**`, never
bundled by Metro and never reachable from `App.tsx`, so the Expo Go constraint holds; `export:check`
staying green is the mechanical proof.

### 4.5 `src/__tests__/render-smoke.test.tsx` — required behavior

Fixture signature only:

```tsx
function Hello(props: { name: string }): React.JSX.Element
```

rendering `<View><Text testID="greeting">Hello, {name}</Text></View>` from `react-native`. `render()`
it via RNTL, locate the node by testID/text, and use at least one **built-in RNTL matcher** (e.g.
`toBeOnTheScreen`) so the test fails loudly if someone adds the deprecated
`@testing-library/jest-native`. No snapshots — noise on a fixture, and it commits a `__snapshots__` dir.

### 4.6 `.github/workflows/ci.yml` — exact change

Replace the trailing comment block with:

```yaml
      - name: Tests
        run: npx jest --ci
```

Nothing else changes — not the Node version, not `npm ci`, not step order.

CI note (expectation, not a change): with `~12.9.0`, `prebuild-install` finds and **downloads** the
published Node 20 (ABI 115) linux-x64 prebuild, so the `node-gyp` fallback is never reached and
`npm ci` needs no C++ toolchain and no nodejs.org headers. A `node-gyp rebuild` line for
`better-sqlite3` in a CI log means the pin was widened or the Node major changed — fix the pin, do
not add build-tools or caching steps here.

## 10. Open questions

Neither blocks this PR.

1. **CI step ordering.** Tests run after `export:check`, the slowest step; moving them earlier would
   fail faster. Unchanged here because the issue says keep the workflow otherwise unchanged — a
   one-line follow-up on request.
2. **Node 20 vs 22 — now load-bearing twice.** Node 20 reached end of life upstream in **April
   2026**. Staying on it costs two coupled pins: `better-sqlite3@13` is unavailable
   (`engines: node >= 22`), and within 12.x we are capped at `~12.9.0` because 12.10.0 dropped Node
   20 prebuilds precisely *because* Node 20 is EOL (§4.3). The second is a ratchet — each upstream
   release moves further from us, and the fallback is a source build that makes a devDependency
   install depend on a C++ toolchain and nodejs.org. Moving dev and CI to Node 22 removes both at
   once. It is a human decision (it touches the development environment), and doing it *before* #2
   writes driver tests is cheaper than after.

## 11. Amendments

### 2026-09-02 — `better-sqlite3` pinned to `~12.9.0`, not `^12.11.1`

**What changed:** §4.2, §4.3, §4.6, §6 (item 6) and §10 Q2 now specify and justify `~12.9.0`. The
original plan said `^12.11.1`.

**Why the original was wrong:** I pinned on `engines` alone, the wrong signal. `12.11.1` declares
Node 20 support so it installs without a warning, but ships no ABI 115 prebuilt binary — upstream's
v12.10.0 notes: "Add support for Node.js v26 prebuilds and remove EOL builds (Node.js v20, v23)".

**Concrete failure mode:** the install script is `prebuild-install || node-gyp rebuild`. On Node 20,
`prebuild-install` finds nothing and silently falls through, turning `npm ci` into a C++ compile
needing a toolchain *and* a header download from nodejs.org — test-programmer hit exactly this, and
the install only completed with a manual `--nodedir`. On `ubuntu-latest` it would likely compile
successfully but slowly, the worse outcome: green CI hiding a build one nodejs.org outage,
runner-image change, or fresh contributor machine away from failing in a way that reads as "tests
are broken" rather than "the pin is wrong". A PR whose job is making the suite trustworthy must not
make `npm ci` conditional on a compiler.

**Cost:** nothing usable — 12.10+ adds Node 26 prebuilds and drops EOL ones; deps are identical.
**Unblocking condition:** Node 22 (§10 Q2), where the pin should be widened deliberately in its own
issue, not by `npm update`.
